# 爱玩羽社 - 羽毛球循环赛管理系统

移动端 H5 羽毛球 2v2 循环赛管理平台。随机轮换搭档、实时记分排名、PK 加油助威、邀请制注册。

## 技术栈

- **后端**: FastAPI + SQLAlchemy 2.0 (async) + PostgreSQL
- **前端**: Vue 3 + Vant 4 + Pinia + TypeScript
- **部署**: Docker Compose

## 快速开始

### 开发环境

```bash
git clone <repo-url> && cd BadMatch
docker compose -f docker-compose.dev.yml up --build
```

访问 `http://localhost:5173`

### 生产环境

```bash
# 1. 复制 .env.example 为 .env 并填写：
#    SECRET_KEY（必填！openssl rand -hex 32 生成）
#    DB_PASSWORD、SUPERADMIN_INIT_CODE（可选，见下）
cp .env.example .env

# 2. 启动
docker compose -f docker-compose.prod.yml up -d
```

访问 `http://localhost`（端口由 `.env` 中 `PORT` 控制，默认 80）

> 服务启动时会自动执行幂等迁移（补齐 `users.email`、唯一约束、`matches.started_at/ended_at`、`users.token_version` 等缺失列，以及 `matches.tournament_id` 的索引 `ix_matches_tournament_id`），老库升级无需手动执行 SQL。

### 首次初始化（超级管理员）

首个注册用户自动成为超级管理员，但必须提供**初始注册码**（防止被抢先注册）：

- 在 `.env` 中配置 `SUPERADMIN_INIT_CODE=你的注册码`（推荐，部署时固定下来），或
- 不配置时：**第一次有人提交注册请求**才会随机生成 8 位码并 WARNING 打到服务日志
  （不是启动时就打印 —— 所以刚 `up -d` 完去翻日志是看不到的，得先有人试一次注册；
  该随机码存在进程内存里，重启即变；首个超管注册成功后它就不再参与任何逻辑）

### 忘记密码（邮箱找回）

登录页提供「忘记密码？」入口：输入邮箱 → 收到带重置链接的邮件 → 打开链接设置新密码。

- **前提一：必须配置 SMTP**（`SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD`）。未配置时接口仍正常返回，
  但邮件发不出去、日志会提示 `密码重置邮件未发出`，用户拿不到链接。
- **前提二：该账号必须填过邮箱**。邮箱是可选字段，从未设置过邮箱的账号无法用此方式找回
  （只能由超级管理员在管理面板重置密码）。
- 安全设计：
  - 无论邮箱是否注册都返回同一句文案，避免被用来批量探测某邮箱是否注册过
  - 命中与未命中两条分支的**库操作与耗时也保持一致**（发信已移出请求路径），
    否则「响应体一样但耗时差几百毫秒」照样能被批量测出邮箱是否注册
  - 发信走后台任务 + 线程（`smtplib` 是同步阻塞调用，放在请求路径上会独占事件
    循环，实测一次阻塞 1 秒会让心跳定时器抖动 999ms，期间所有人记分/推送停摆）
  - 令牌 20 分钟有效、**只能用一次**（并发提交同一令牌也只有一次能成功），
    重新申请会作废该用户此前所有未用令牌
  - 数据库里只存令牌的 sha256，**不存明文**（库泄露也无法拿去重置别人密码）
  - 令牌放在邮件链接的 `#` 之后（URL fragment）：不会随请求发给服务器，
    因此不进 nginx/应用访问日志，也不会通过 Referer 泄露；邮件安全网关预取
    链接时也不会带上 fragment，因此不会误消费这张一次性令牌
  - 重置成功后 `token_version` 自增：所有已登录设备立即失效并断开 WebSocket，
    需要重新登录
  - 新密码上限 30 位（bcrypt 只取前 72 字节，前端输入框已按此限制）
  - 限流：申请 10 次 / 15 分钟（按来源 IP），提交 10 次 / 15 分钟（按来源 IP）
- 邮件发送使用系统 CA 校验证书（`ssl.create_default_context()`）。注意 Python 的
  `SMTP_SSL`/`starttls` 在未显式传 context 时**默认不校验证书**，而这条链路上跑的
  是可改密码的凭证，因此必须显式校验。若你的 SMTP 用的是自签证书，请改为把该证书
  加入信任链，而不是关闭校验。
- 升级说明：早期版本「修改资料」保存邮箱时只做 `strip` 不做小写化，可能存下带大写的
  邮箱。启动迁移会统一规范成小写；若历史上已存在 `A@x.com` 与 `a@x.com` 各占一个
  账号，则保留 id 较小的那个，其余账号的邮箱被置空（并在日志中告警）——被置空的账号
  将无法再用邮箱找回，只能由超级管理员在管理面板重置密码。

### 安全注意

- **WebSocket 用一次性票据连接**：浏览器无法给 WebSocket 握手加自定义头，凭证只能放进 URL，
  而 nginx 会把请求行写进 access log —— 等于把长期有效的 JWT 明文落盘。
  因此改为先用 `POST /api/auth/ws-ticket`（JWT 走 `Authorization` 头，不落日志）换一张票据，
  再用 `?ticket=xxx` 连接。票据**一次性、60 秒过期、不能换 JWT**，即使被日志记录也无利用价值。
  过渡期仍兼容旧的 `?token=<JWT>` 方式，待所有前端刷新过后可删除该兼容分支。
- **`SECRET_KEY` 校验是 fail-closed 的**：留空、使用默认/示例值、或长度不足 32 字节时，服务**拒绝启动**（不再看 `DEBUG`）。
  这是刻意的——默认密钥是公开的，一旦被用上，任何人都能离线伪造出任意用户（含超级管理员）的登录凭证。
  本地开发如确需使用默认密钥，显式设置 `ALLOW_INSECURE_SECRET_KEY=true`（dev compose 已这样配置）。
- **来源 IP 默认不信任转发头**：`CF-Connecting-IP` / `X-Forwarded-For` / `X-Real-IP` 任何客户端都能自己伪造，
  一旦采信，所有按 IP 的限流（登录、初始注册码、邀请码、头像上传）只要每次换一个伪造值就能无限尝试，
  审计日志里的来源 IP 也会变成攻击者随手填的内容。
  - 默认 `TRUST_PROXY_HEADERS=false`：直接用对端 IP（安全，但经反向代理时记录的是代理 IP）
  - 服务只允许反向代理回源时设为 `true`：此时优先取 `X-Real-IP`（nginx 用 `$remote_addr` 覆盖式写入，伪造值会被冲掉）
  - 走 Cloudflare 时需**同时**设置 `TRUST_CF_CONNECTING_IP=true`，否则限流会按 Cloudflare/nginx 的 IP 计数
- **token 版本号机制**：登出、修改密码、管理员重置密码都会使该用户所有 token 立即失效，并主动断开其全部 WebSocket 连接；升级/重启后旧 token 按版本 0 兼容处理，**已登录用户无需重新登录**

### Cloudflare 部署（推荐）

**场景 A：Cloudflare Tunnel（Zero Trust）——内网/无公网 IP 服务器**

- 服务器**无需公网 IP、无需开放任何入站端口**：`cloudflared` 主动出站连接 Cloudflare，回源 HTTP
- 浏览器侧 HTTPS 和 HTTP/2 由 Cloudflare 提供，服务器**无需配置证书/443**
- 真实客户端 IP 由 **client 容器里的 nginx 还原**：`nginx.conf` 用 `realip` 按 `CF-Connecting-IP`
  覆盖 `$remote_addr`（信任范围 = 私有网段 + Cloudflare 网段），再以 `X-Real-IP` 覆盖式转发。
  因此后端只需 **`TRUST_PROXY_HEADERS=true`**（prod compose 默认即是）；**不必**再开
  `TRUST_CF_CONNECTING_IP` —— nginx 转发前会把该头清空（防伪造）
- ⚠️ 安全：把 client 端口绑到回环（`127.0.0.1:${PORT}:80`）或只放行隧道来源。realip 的信任
  范围含私有网段，若该端口对同内网开放，直连者可自带伪造的 `CF-Connecting-IP`，把自己的
  来源说成任意地址（按 IP 的限流与审计随之失效）

**场景 B：Cloudflare 代理（橙色云，服务器有公网 IP）**

- Cloudflare 面板 **SSL/TLS 模式保持 Flexible**（回源 HTTP）；若设为 Full/Full(strict) 会回源 TLS 失败（521/525）
- ⚠️ 防火墙/安全组**只放行 Cloudflare IP 段**（https://www.cloudflare.com/ips/ ），否则直连可伪造 `CF-Connecting-IP`
- 真实客户端 IP 同样由 nginx 的 `realip` 还原（`nginx.conf` 里已列出 CF 网段），后端仍是 `TRUST_PROXY_HEADERS=true`

**场景 C：直接经 nginx 暴露（无 Cloudflare）**

- nginx 已用 `$remote_addr` 覆盖式写入 `X-Real-IP`，因此设置 `TRUST_PROXY_HEADERS=true` 即可拿到真实客户端 IP
- `docker-compose.prod.yml` 默认即为 `true`；**若服务会被绕过 nginx 直接访问，必须改回 `false`**

## 核心功能

- **用户名注册登录**：修改密码、上传头像、性别设置
- **邀请制注册**：生成邀请码/链接，可重新生成作废旧码
- **赛事管理**：创建、**修改（仅报名中）**、删除、提前结束，自定义计分制和场次数
- **修改赛事**：报名中的赛事可由房主/管理员/超管修改（详情页右上角铅笔图标，或底部
  「编辑赛事信息」按钮），与创建页是**同一个表单**（`/tournament/:id/edit` 复用
  `CreateTournament.vue`），可改名称/地点/场地号/备注/日期时间/最大人数/计分制/总场次。
  - **最大人数不能小于当前已报名人数**（报错里直接写出现在几人）：报名行是既成事实，
    改到人数之下会得到「9/8 人」这种自相矛盾的状态，被裁掉的人也没有地方可去；
    正好等于已报名人数是允许的 —— 那正是「人满了，别再报」这个常见用途
  - **已开赛/已结束一律只读**（超管也不例外，这点与删除不同）：赛程是开赛那一刻按当时
    人数排好的，改人数/名称不会让赛程跟着变，留个口子只会让人以为改完就生效；
    要调赛程请用「追加比赛 / 重排赛程」。超管真要改，删掉重建即可
  - 场地号/时间段是**整体替换**：报名中还没排赛程，没有比赛引用 `court_id`；
    万一脏数据里已有比赛，接口会明确回 400 而不是让外键约束打成 500
  - 编辑路径**忽略** `preselect_player_ids`（预选只在创建时有意义）
  - 保存后广播 `tournament_updated`，正在看详情页的人自动刷新；写一条
    `tournament_update` 审计（只记**真变了**的字段，前后值都留着）
- **报名链接分享**：赛事详情页「复制链接」一键把当前页面地址复制到剪贴板，发给球友来报名
- **报名海报分享**：赛事详情页右上角生成 PNG 海报（时间 / 地点 / 名额 + 报名二维码），
  发到微信群后球友长按识别即可进报名页 —— 不需要公众号，只用图片 + 二维码。
  二维码来自 `GET /api/tournaments/{id}/poster-qr`，里面带**生成者自己的邀请码**：
  未注册的球友扫码后会被路由守卫带到登录页并自动预填邀请码，注册完自动回到报名页。
  注意邀请码只有管理员能生成（`auth/generate-invite`），普通成员的海报不含邀请码
  （界面会提示这一点），只适合提醒**已注册**球友报名
- **取消报名记录**：谁取消过报名在详情页可查（取消是标记失效而非删记录，会记下取消时间；
  取消后又重新报名则不再算取消记录）；入口只在有人取消过时才出现，弹层懒加载
- **日历选日期 + 时间段**：日期默认本周五，时间段默认 19:00~21:00，分钟步长 5
- **创建页默认值**：赛事名称默认按**选中的日期**生成「10月16日养生局」（改日期会跟着变，
  两次改日期只有最后一次的结果落地；自己改过名字就不再覆盖，见
  `GET /api/tournaments/default-title`）；同一天要排第二场时默认名撞车才加序号
  （`10月16日养生局（2）`），否则列表和海报里两行同名分不清。
  序号只看**同一天**的赛事——查询同时卡住开始日期和名字前缀：名字里没有年份，
  只按前缀查的话，去年 10/16 那场同名赛事会让今年的默认名直接从（2）起步。
  注意这只保证"默认建议"不撞车：标题没有唯一约束，两个人同时创建、或表单开着很久再提交，
  仍可能拿到同名（真在意就提交前再点一下日期刷新建议）；
  地点默认「奥体中心」。名称和地点都只是预填，随时可改
- **智能赛程**：贪心构造 + 多方案择优。保证每人场次**完全相等**；每场从「还没打满的人」里选 4 人时，
  把 3 种分组方式**全部**评估，并按「完全相同的对局 / 重复搭档 / 重复对手 / **对手次数极差**」四项打分；
  同一批人还会**换序多排几次、挑最好的一份**（小规模最多 60 次，人数越多档位越低，见
  `_quality_attempts`；达标就提前收工，所以常态只要 1~2 次）。
  **场内公平**（这是"每个人遇到的对手都公平"的硬指标）：8 人 14 场实测**每对搭档恰好 1 次、
  每对对手恰好相遇 2 次** —— 56 个搭档名额正好 28 对、112 个遭遇名额正好 28 对，这就是数学最优。
  其它规模实测的"对手次数极差"（最多见几次 − 最少见几次）：5 人 5 场 0、6 人 6 场 1、8 人 16/22 场 1、
  9 人 18 场 2、12 人 33 场 2 —— 再往上受"每场 4 人、2v2"的结构限制，极差不可能压到 0。
  8 人 16~60 场都不会出现完全相同的对局，搭档重复次数压到理论下限
  （14 场每对搭档 1 次、28 场每对搭档 2 次；14~28 场之间每对至少 1 次、其中 2M−28 对 2 次，
  且每个球员的"重复搭档"个数完全相同）。
  **跨赛事避重**：开赛、追加比赛、退赛重排、重排赛程都会把「本赛事已排的」+「**最近 3 场赛事**的」
  搭档/对手/对局统计一起当历史喂给排程器（`RECENT_EVENT_HISTORY`），所以每周固定这群人打球时，
  「上周那一场 4 个人、同样的分组」基本不会原样再来一次：实测（连续每周的稳态）与最近 3 场
  完全重复的对局，8 人 14 场 / 9 人 18 场 / 12 人 33 场都在 **0.1% 以内**（不带避重时 8 人 14 场是 19.2%）。
  **长赛事是例外**：8 人 28 场只能压到 **13.6%**（平均每场约 3.8 场；不做避重是 38.9%）——
  因为"场内完美均衡"（每对搭档 2 次、每对对手 4 次）本身把可选赛程卡得很死，两者在这个规模上
  是真冲突，我们按"场内公平优先"取舍（把候选份数从 60 提到 200 已经从 17.9% 压到 13.6%）。
  **历史只用来"在若干份候选里挑一份"，不参与贪心打分** —— 这是关键：历史一旦参与打分，
  会把贪心推出场内均衡的结构（实测那时"某对相遇 4~5 次、另一对只 1 次"的赛事占 91%）。
  改成"贪心永远不带历史地排出均衡候选，再挑最不撞历史的那一份"之后，场内公平与跨赛事避重**同时**成立
  （上面 0.8% 与"每对恰好 2 次"是同一批实测里的数字）。全流程不改变每人场次。
  每一档还套一层兜底「先带全部历史 → 排不出来才不带历史重试**同一档**」，只保证不改大
  用户选的场次、也不会报错（历史退出贪心打分后这一层基本不会再触发 —— 贪心的可行性与历史
  无关，两个级别要么都成要么都败；只有 >48 人那种"历史仍参与贪心"的档位才可能用上，
  且那一档才有 `history_level` ≠ 0 的可能，平常它就是 0）。
  开赛一次耗时：8 人 14 场 2ms、8 人 28 场 15ms、12 人 33 场 50ms、16 人 60 场 0.3s、
  24 人 96 场 2.9s、48 人 96 场 4.8s（场次特别多的小规模赛事、例如 8 人 60 场约 2.5s；
  都是一次性开赛动作）；人数 > 48 时只排一份，那一档历史仍参与贪心，
  否则跨赛事避重在那种规模上会整个失效。
  **开赛时还会把名单顺序真随机打散一次**：跨赛事避重管"别跟最近几场撞同样的对局"，
  洗牌管"别总是报名最早的那 4 个人打第一场"（算法本身是确定性的，不洗牌的话同一群体每周
  同样顺序报名就会拿到一模一样的第一场）。洗牌种子记在开赛审计的 `shuffle_seed` 里，
  有它就能复现某一份赛程；洗过的顺序会跟着 `player_stats` 落库，本赛事后续的追加比赛、
  退赛重排都按它算（**同一赛事内可复现**，只有"每次开赛"是随机的）。
  注意**搭档完全跨周不重复做不到**：8 人 14 场时每人打 7 场、正好要跟其余 7 人
  各搭档一次，而搭档组合只有 C(8,2)=28 种，一周就用满——这是组合数学的限制，不是算法能绕开的。
  算法本身仍是确定性的：**同一份名单顺序 + 同样的最近赛事历史 + 同样的场次数** → 同一份赛程，
  可复现；"每次开赛"的随机只来自开赛那一次洗牌和落库前的左右翻边。
  **左右两侧也是随机的**：落库前对每一场随机翻边（`shuffle_sides`）——打分并列时总是名单
  靠前的人进 A 队，不翻边的话名单第一人会在自己参加的每一场里都站左边（对阵本身不变）
- **对阵表按人筛选**：「只看某些人」与「排除一个或多个人」都支持多选，两者可叠加；
  「只看」多选有**三种匹配方式**（面板顶部可切，**默认仍是「或」**）：
  「或（任意一人）」＝ 选中的人里任何一位参加就显示（取并集）；
  「且（必须同场）」＝ 这些人必须同时出现在同一场的 4 人里（2v2 一场只有 4 人，
  选超过 4 人时面板会红字提示必然筛不出来）；
  「搭档（同一队）」＝ **正好选 2 个人**，只看这两人**同一队**的比赛（"我们俩配合的场次打得怎么样"）。
  它和「且」的区别是实打实的：同一场里分属两队（互为对手）的两个人，「且」看得到、「搭档」看不到；
  选 1 个或 3 个以上都筛不出比赛（面板里同样有红字提示）。
  再叠加「排除王五」＝ 王五不参加的比赛；
  匹配方式与条件一起按赛事记住（`onlyMode` 存 `any`/`all`/`partner`，老数据没有这个字段时按「或」处理）；
  面板里改动、点「确定」才生效；
  顶部有摘要和「只看我」快捷开关——它是**一键收敛**：不管当前选了多少人、排除了谁，
  点一下都变成「只看我一个人」（排除会一起清掉，否则被别人挡住的、我自己参加的比赛仍看不到），
  再点一下取消筛选回到全部比赛。条件按赛事记住（刷新/返回后仍在）。
  筛选不改变「第N场」的编号，折叠较早已完成比赛等规则同样作用于筛选结果。
  赛程里已经没有的人（赛中退赛会重排赛程）会从筛选条件里自动剪掉，避免条件永远卡住
- **实时记分**：+1/-1 按钮，防抖节流，交换场地，手动结束比赛（确认弹窗），结束后自动返回
- **比赛时长统计**：记分页实时计时（localStorage 持久化，首次记分起算，超 3 小时自动重置）；结束后对阵表显示比赛耗时
- **PK 加油条**：观众可为比赛队伍投票加油，进度条实时显示票数，头像展示投票者
- **排名统计**：胜场→净胜分排序，跨赛事胜率汇总，🥇🥈🥉 奖牌展示（退赛选手不占名次）
- **积分榜分享图**：右上角一键生成 PNG 卡片（赛事名 + 名次/胜率/净胜分，当前用户高亮、退赛淡出），
  可调系统分享面板发到微信，或长按图片保存后再发
  （微信内置浏览器里「分享给微信好友」不可用：安卓微信没有 Web Share API；iOS 微信虽有、
  但把文件交给微信自己的分享扩展会被取消（面板闪一下就没了），所以微信内主推「长按图片 → 存储图像」，
  分享按钮只承诺其他应用；`http://局域网IP` 不是安全上下文，也不会有系统分享）
- **苹果手机（iOS）上没有「保存图片 / 分享到微信」按钮**，只有「存到相册 / 分享」
  （`http://局域网IP` 这类没有系统分享面板的环境下，按钮文案是「怎么存到相册？」）：
  iOS 上老的两个入口都到不了相册 —— `<a download>` 把文件丢进「文件」App；系统分享面板里
  选「微信」发出去的是一条**文件气泡**（`报名海报.png` + 文档图标，对方还得自己再存一次）。
  根因在 **iOS 微信的分享扩展**：只有**相册里的照片**才当图片收，网页分享过去的文件一律
  按"文件"处理，网页侧改 mime / 文件名都改不掉。能进相册的只有系统动作——分享面板里的
  「存储图像」、或长按图片存到相册（微信自家菜单里这一项叫什么名字各版本不一，所以提示语
  只写「存到相册」，不写死动作名）。环境判定、按钮表与文案都在
  `client/src/utils/shareEnv.ts`（纯函数，见 `client/tests/unit/shareEnv.test.mjs`）。
  **安卓/桌面不受影响，保持原按钮**（安卓微信正常：系统分享把 `image/png` 作为
  `ACTION_SEND` 交给微信，聊天里收到的是图片，实测正常）；而"不存相册、直接从网页把图
  当图片发进**iOS** 微信聊天"是真的做不到：iOS 微信的分享扩展不认网页分享过去的文件，
  想绕开只能接公众号 JS-SDK（要认证公众号 + 后端签名），且那分享出去的是链接卡片、不是这张图
- **赛中追加比赛**：开场次排少了、时间还有富余时，创建者/管理员可在赛事详情页「追加比赛」，
  按档位再加几场（新比赛接在最后一个轮次之后，已打过的比赛不受影响）。追加数只能是
  `N/gcd(4,N)` 的倍数（8 人 → 2 场、6 人 → 3 场、9 人 → 9 场），这样每人新增场次仍然相等；
  可选项由服务端算，界面不会给出会被接口拒掉的档位。排新场次时会带上已有赛程的
  **搭档 / 对手 / 完全相同对局** 三种历史做惩罚，避免和已经排过（或打过）的比赛撞车；
  总场次上限仍为 100 场，每次追加写一条 `tournament_add_matches` 审计
- **重排赛程**：赛事详情页「重排赛程」（房主/管理员/超管）——这份赛程不合适
  （比如和上一场撞得太多）时换一份。**只有一场都没开打时才给**（赛事进行中 +
  `started_match_count == 0`）：一旦有比赛在打或已打完，这个入口就不显示、接口也会回 400 ——
  重排会把**当前这份**赛程整批删掉重排，那等于毁掉正在进行/已经产生的比分与历史
  （所以入口名字里也没有"未打完"这种说法 —— 打到一半的场次是不能重排的）。
  重排时这些场次上已认领的裁判会被取消并收到「请重新认领」站内消息；避重历史照旧
  （这份旧赛程 + 最近 3 场赛事），另外服务端**故意洗牌名单顺序**：算法是确定性的，
  不洗牌的话连点两次会排出完全一样的赛程，点了就像没反应（自动路径开赛/追加/退赛仍然可复现）。
  每次重排写一条 `tournament_reschedule` 审计（含被替换的场次数、被取消的裁判数）
- **禁用账号（替代删除）**：删除用户会被「有比赛记录 / 创建过赛事」两条护栏挡住，而实际场景
  常常只是"让他别再来了"。管理面板的「禁用」正是这个用途：**数据全部保留**（比赛、战绩、审计
  都在），只是登录被拒（已登录的设备立刻失效并被踢下线）、不再出现在「默认参赛人员」选择列表里、
  也不会被选为新房主；他的邀请码同时失效（不能再拉新人注册）；
  已认领的**未打完**场次会自动标记卸任（名字仍作为执裁历史保留，已结束比赛的裁判记录属于归档、
  不被动）。
  被禁用的账号同时从所有「在场名单」里剔除：开赛、赛中追加比赛、退赛重排都不会把他排进赛程；
  报名中的赛事在**开赛时**会自动取消他的报名（保留那一行、记取消时间，能在「取消/退赛记录」里
  查到，开赛审计里也记了条数）—— 否则会出现"名单 8 人、赛程只有 7 人"且赛后无法清理的死结。
  如果他还是某个赛事的房主，房主会自动转给一个未禁用的在场选手，并给对方发一条站内消息
  （提醒他：报名中的赛事开赛时会自动取消，进行中的请用「退赛」把人移出）。
  已经在进行中的赛事不会自动改赛程：他仍留在名单与**已经排好**的比赛里，需要组织者用「退赛」
  把他移出（退赛会重排未开打的轮次；已打完的历史比赛不动）。
  权限与删除一致：超管可操作任意人，普通 admin 只能操作自己邀请的普通用户；不能禁用自己或超管。
  随时可以「恢复」，恢复后即可重新登录（但之前被取消的报名不会恢复，需要重新报名；
  被转走的房主也不会转回来）。
  每次禁用/恢复都写审计（`admin_disable_user` / `admin_enable_user`，含自动卸任/转房主/发提醒的条数）；
  管理面板会把已禁用的账号标出来
- **裁判认领**：任何登录用户都能认领（**含本场参赛选手**——借别人的手机代认领是真实场景）；
  已被认领的场次**允许后来者顶替**（前端先弹确认框写明会顶掉谁），被顶替者会收到站内消息，
  审计里也记下 `replaced_referee_id`；顶替后对阵表右侧那行**显示的是新裁判**（不会变成空白，
  也不会给新裁判挂上「已卸任」）；被顶替后任何人都可接手（**界面上没有「卸任」入口，
  换裁判只能靠顶替**）。上场选手和在任裁判不可投票
- **自动分配裁判**：对阵表**筛选行右侧**一个胶囊按钮（与「只看我/清除」同一行，不额外占一行），
  **本赛事在场选手**（未退赛、账号未禁用）都能点——给**当前要打的那一批**（最早一个还有比赛
  没打完的轮次，内部概念）里「还没裁判」的场次指派**场下人员**（本场 4 人之外的在场选手）。
  **均衡轮转 + 并列随机**：优先挑**本赛事已安排执裁场次最少**的人，次数并列的人之间等概率随机
  —— 所以谁吹哪一场仍是随机的（不可预测），但不会出现"有人吹 4 场、有人一场没吹"那种纯随机的
  偏斜（实测 8 人 14 场：改前"最多-最少"常见 3~4 次、**12.9% 的人整场轮空**；改后极差 ≤2、
  没人轮空。计数口径 = 本赛事里裁判是他且**在任**的场次，自己认领的和本次已分的都算）。
  同一批里一个人最多当一场的裁判。
  刚在某一场上**卸任**的人不会被自动分回**那一场**（他明确说了不行；而且均衡计数按"在任"算，
  卸任后他会变成"吹得最少"的那个，不挡一下就会立刻把他送回去）——想吹回来手动认领即可。
  **只填空缺**：已有在任裁判的场次不动（想换裁判用「顶替」）；在场人不够时跳过该场并在提示里说明。
  按钮**只在真有场次缺裁判时出现**（赛事进行中 + 我是本赛事在场选手 + 当前这一批还有缺口），
  胶囊上直接写场次数（「分配裁判 2」）；没活干时整块隐藏 —— 后端只填空缺、从不覆盖已有裁判，
  留一个点了没反应的按钮只会让人困惑（当前这批打完后会自动轮到下一批，有缺口时它自己就回来）。
  点开的确认弹窗与站内消息**一律用对阵表的场次编号**（「给第 3、4 场分配…」）——
  界面里没有「第 N 轮」这个概念，说轮次用户对不上号；真遇上「已有裁判」也会明说
  「第 3 场已有裁判，无需再次分配」而不是去发一个没用的请求。
  审计记 `referee_auto_assign`（含被跳过的场次）
- **一次性分配裁判（赛事详情页）**：进行中的赛事、且还有场次没裁判时，**房主/管理员/超管、以及
  本赛事在场选手**（未退赛、账号未禁用）都能在详情页点「一次性分配裁判（N 场）」——把**全部**
  还没打完、还没裁判的场次一次分完
  （规则同上：场下人员、均衡轮转、同一批每人最多一场、只填空缺；跨批次继续累加计数，
  所以一次分完整局后每个人的执裁场次就被拉平了）。
  分完后 `pending_referee_count` 归零，**详情页这个入口和对阵表里的「分配裁判」按钮都会自动消失**
  （所以实际上只能点一次）；若之后再用「追加比赛」加了新场次，它们又会没裁判、入口自然回来。
  站内消息**按人合并成一条**（一次分十几场时不会刷屏）：「您被分配为第 3、7、12 场的裁判」。
  在场选手也能点是后来放开的（最初只给管理者）：整局分比赛本来就是场上这帮人的事，组织者
  常常就是选手本人，让他先退出比赛界面去详情页点反而绕。风险可控——这个接口**只填空缺、
  从不覆盖已有裁判**（换裁判走「顶替」），按钮上写着还剩几场，点之前还有确认弹窗。
  已退赛的人不行（`candidate_ids` 里没有他）；房主/管理员即便不在场也仍然可以
- **管理员面板**：查看用户、禁用/恢复账号、删除用户、重置密码、设置/取消管理员；超级管理员可查询**操作日志**（按用户名/操作类型/时间范围筛选，分页加载）和**访问日志**（实时浏览记录，按关键词/请求方法筛选，读文件不落库）
- **访问审计**：全量 HTTP 访问日志（JSONL 落盘，含 IP/用户/路径/耗时）；关键业务操作写入 `audit_logs` 表，默认记录 90 天

### 审计覆盖的操作（35 种）

| 分类 | 操作 |
|---|---|
| 认证 | 注册、登录成功、登录失败、登出、修改密码、修改资料、上传头像、生成邀请码、申请重置密码、重置密码 |
| 管理员 | 重置密码、设置角色、删除用户、禁用用户、恢复用户 |
| 赛事 | 创建、批量创建、修改、删除、开始、结束、追加比赛、重排赛程、退赛、报名、取消报名 |
| 比赛 | 开始轮次、结束比赛、记分*、投票*、交换场地、认领裁判、卸任裁判、自动分配裁判 |
| 运维 | 重置对阵左右（只有一次性脚本 `scripts/randomize_match_sides.py` 会写，见该脚本说明） |

> `*` 为高频操作（记分/投票），默认不记录，由 `AUDIT_HIGH_FREQ_ENABLED` 环境变量控制
>
> 高频记分/投票不写表；其余操作每次触发均写入 `audit_logs`，可在管理面板「操作日志」页查询

**「结束赛事」有两条路径，都会记录**：管理员/创建者点「提前结束」，以及**比赛全部打完时
系统自动收尾**（后者最常见，detail 里带 `auto: true`）；退赛后人数不足 4 人也会自动结束。
早期版本漏了自动收尾这条路径，导致按「结束赛事」筛选时一条都查不到。

**审计写入本身也会失败，因此必须可追溯**（曾经踩过：生产库里约 27% 的审计写入没有落库，
其中一段时间连续 121 次全部失败，而失败只打到了容器 stdout，容器一重建根因就不可考）：

- **写入顺序是硬约束**：成功路径一律「先提交（有广播的放在广播之后）再写审计」。
  审计用独立会话立即提交，写在提交前的话，业务事务一回滚就会留下一条「操作成功」的假日志；
  而 `register` / `update_profile` 还额外**必须**先提交 —— `audit_logs.user_id` 有指向
  `users` 的外键，用户行没提交时那条审计会写入失败并被静默吞掉
  （表现为「注册在操作日志里根本查不到」）。失败路径（如 `login_failed`）是唯一例外，
  必须在 `raise` 之前写。这条由 `server/tests/test_audit_order.py` 静态守住。
- `ip` / `user_agent` 会先裁剪到列宽（45 / 255）：PostgreSQL 对超长字符串是报错而非截断，
  一个超长请求头会让**整条**审计丢失
- 写入失败会**重试一次**（连接被回收、锁等待超时这类瞬时故障能救回来），仍失败则落到
  `logs/audit-failures.log`（生产 compose 已把 `./logs` 挂到宿主机，跨容器重建保留），
  同时在 stdout 打 ERROR
- 请求被客户端中途取消（手机端切页/断网）也会记一条到该文件：业务可能已提交，
  而这条审计不会落库
- 自查是否丢过写入：`select (select last_value from audit_logs_id_seq) - (select max(id) from audit_logs);`
  差值就是「尝试过但没落库」的次数（含被取消的请求）；配合 `logs/audit-failures.log` 看原因

- **超级管理员**：可删除**任意状态**的赛事（创建者/管理员只能删报名中的：已开赛/已结束的
  赛事连同轮次、比赛、战绩会一起级联删除）、预选参赛人员。
  但**修改赛事只限报名中**，超管也不例外（赛程已按当时人数排好，改了也不会跟着变）
- **预选邀请邮件**：创建赛事时选了「默认参赛人员」，对方填过邮箱就会收到邀请邮件
  （赛事名称、开始时间、地点、**场地号**、直达赛事详情的链接）；没填场地号的赛事不显示那一行
- **赛事自动结束**：所有比赛打完自动完结赛事并广播
- **下拉刷新**：全站页面支持下拉刷新，类 App 体验
- **WebSocket 实时同步**：计分、排名、加油条、对阵表实时更新（连接需登录 token 校验）
- **智能返回**：直接通过链接进入页面时返回首页，站内跳转则逐级返回

## 访问控制

除下面四处外，**所有页面都要求登录**（未登录访问会跳转到登录页，登录后自动回到原目标）：

| 匿名可访问 | 为什么留公开 |
|---|---|
| `/profile` | 登录/注册页，也是邀请链接的落地页（`?invite=邀请码`） |
| `/forgot-password` | 忘记密码入口，走到这里时必然还没有登录态 |
| `/reset-password` | 邮件里的重置链接，令牌在 `#` 里，打开时本来就没有登录态 |
| `/tournament/:id/rankings` | 积分榜：只读、无隐私，是这个封闭群唯一对外的展示面（分享图也在这里生成） |

**边界在后端，不在前端**：前端路由守卫只是体验层，直接 `curl` 接口绕得过去。
所以除积分榜外，赛事列表/详情/报名名单/对阵/单场/应援票数/任意用户战绩这些读取
接口都在 `server/app/api/` 里显式要求登录（`Depends(require_user)`）；匿名请求返回
401，前端拦截器会清掉 token、跳到登录页，并在登录后自动回到原目标。

> 想再放开某一页（例如让外人也能看对阵表），前后端要一起改：后端去掉对应接口的
> `require_user`，前端给该路由加 `meta: { public: true }`。只改前端等于没改。

> 手打错的地址（未匹配任何路由）会兜底跳回首页；未登录时先进登录页，登录后落到首页。

## 移动端性能优化

- **vendor 分包**：构建按 vue/vant/axios 拆分稳定 chunk，配合 `/assets/` 30 天 immutable 缓存，发版只重下业务代码
- **Service Worker**：生产环境注册，静态资源缓存优先、页面网络优先并离线兜底，二次访问几乎零网络
- **API ETag**：GET 响应带弱 ETag + `Cache-Control: private, no-cache`，内容未变时返回 304，重复访问只传协商头
- **压缩**：nginx gzip 已开启；走 Cloudflare 代理时边缘自动提供 Brotli
- **生产单进程**：镜像默认不带 `--reload`（开发环境由 dev compose 覆盖为 `--reload` 热重载）；WebSocket 广播为进程内单例，故不使用 `--workers` 多进程，避免丢广播

### 存量头像压缩

压缩只在上传时执行，历史头像需手动 backfill（压缩到 100px / JPEG 75，原地覆盖，数据库引用不变）：

```bash
docker compose -f docker-compose.prod.yml exec server python scripts/backfill_avatars.py --dry-run
docker compose -f docker-compose.prod.yml exec server python scripts/backfill_avatars.py
```

严格模式（旧 png/gif/webp 重命名为 `.jpg` 并同步 `users.avatar` 引用）：

```bash
docker compose -f docker-compose.prod.yml exec server python scripts/backfill_avatars.py --rename-jpg --dry-run
docker compose -f docker-compose.prod.yml exec server python scripts/backfill_avatars.py --rename-jpg --apply-db
```

> 头像路径只存在 `users.avatar` 一列；`audit_logs.detail` 中的历史路径快照不会更新（审计留痕）。

> 注意：原地覆盖模式因为 `/static` 有 7 天浏览器缓存，用户可能最长 7 天看到旧头像；
> 严格模式重命名后 URL 变化，头像立即刷新。

> 严格模式会把**所有**非 jpg 头像（无论大小）转成 JPEG 并改后缀，包括之前原地压缩过的文件；
> 若之前已确认 Cloudflare 缓存，执行后可顺手在 CF 后台按 `/static/uploads/` 前缀 Purge 一次。

### 数据库结构调整（重要）

本项目**不使用 Alembic 管理 schema**，而是：

1. `Base.metadata.create_all` —— 只负责创建新表，不会给已存在的表补列
2. `app/core/startup_migration.py` —— 启动时**幂等**检查并补齐老库缺失的列/约束（新库老库都能直接跑起来）

因此**新增字段时**：改 `models/` 里的模型，并在 `startup_migration.py` 里加一段「列不存在才 ALTER TABLE」的逻辑，
部署后重启服务即自动生效，**无需手工执行 SQL**。

`server/alembic/` 只保留了当初为 Alembic 准备的异步 `env.py` 与 `alembic.ini`，**没有 `versions/` 目录、代码也未引用它**。
如果将来要改用 Alembic，需要自己生成初始迁移并停止使用 `startup_migration.py`，避免两套机制并行。
